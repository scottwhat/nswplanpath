## Map and cadastre

- **Base style** is `mapbox://styles/mapbox/standard` — Mapbox's own default. Our layers
  are added with `slot: 'top'` so they sit above it.
- **Lots** come from the NSW Digital Cadastral Database, layer 8 of
  `NSW_Land_Parcel_Property_Theme/FeatureServer`, queried by viewport envelope in
  EPSG:4326. Only queried at zoom ≥ 15 (`LOT_MIN_ZOOM`): the layer has a 1:100,000 min
  scale and a 2,000-feature cap, so a city-wide query returns a truncated, misleading set.
- **The service advertises `f=geojson` but answers HTTP 503 for it** (probed 2026-09-09).
  We request Esri JSON and convert in `packages/shared/src/esri.ts`. Esri winds exterior
  rings clockwise and holes counter-clockwise; GeoJSON is the opposite, so every ring is
  reversed and holes attach to the exterior ring that precedes them.
- The response CRS is asserted, not assumed — a non-4326 answer throws rather than
  silently drawing lots in the wrong hemisphere.
- Service URLs, layer ids and field names live only in `data/layer-registry.json`, loaded
  and Zod-validated by `packages/shared/src/layers.ts`.

## Geocoding is interim

`geocodeAddress()` uses Mapbox forward geocoding filtered to NSW. It returns a coordinate,
not a `propertyId`, so **nothing may depend on it beyond moving the camera**. It is also
approximate at the address level: "5 Barnstaple Road, Haberfield NSW 2045" comes back as
Five Dock 2046. Build plan step 1 replaces it with the NSW ePlanning property API, which
resolves to the propertyId every downstream lookup actually keys off.

## The chat runs on this project's own backend

`infra/` is a CDK app holding one stack, **`PlanPathChatStack`** (account 403903769495,
`ap-southeast-2`), deployed and verified end to end. It is this project's own backend —
the earlier `NswTrajectoryAiChatStack` belongs to a separate project and nothing here
depends on it any more.

`apps/web/.env.local` carries `VITE_MAPBOX_ACCESS_TOKEN`, `VITE_CHAT_API_URL`,
`VITE_CHAT_IDENTITY_POOL_ID` and `VITE_AWS_REGION`. All four are live and in use. The two
chat values are the stack's `ChatApiUrl` and `ChatIdentityPoolId` outputs:

```
VITE_CHAT_API_URL=https://mdtjewemq2.execute-api.ap-southeast-2.amazonaws.com
VITE_CHAT_IDENTITY_POOL_ID=ap-southeast-2:6a0865d7-34a5-45c8-b52c-e2ab2c6d60dc
```

This is **not** the `POST /assess` pipeline in SYSTEM_DESIGN.md §1 — that Lambda, the
rules engine and the Knowledge Base still do not exist. What is deployed is a two-hop
conversational endpoint:

1. `POST /chat` on the HTTP API (`AWS_IAM` auth, the only route). The browser signs it
   SigV4 with Cognito **unauthenticated** credentials from the identity pool. The pool's
   unauth role is allowed exactly one action: `execute-api:Invoke` on `POST /chat`.
   The handler is a broker, not a chat endpoint — it checks the SSM kill switch
   (`/planpath/chat/enabled`), meters the quota, then returns 15-minute STS credentials
   scoped to a single `bedrock-agentcore:InvokeHarness`.
2. `InvokeHarness` on the AgentCore harness `nswplanningpathways-qQEuV1iR6r`, in
   **`us-east-1`** — a different region to the API. The response is an event stream,
   rendered token by token. The harness owns its own system prompt, model and Knowledge
   Base gateway, so the client sends only the question text.

Contract details that bite:

- **The harness ARN is not a frontend value and must never become one.** It is set in
  `infra/bin/infra.ts`, returned by the broker, and the credentials the broker mints are
  IAM-scoped to that exact ARN — a client-side override would only ever produce
  `AccessDenied`. To change harness: edit `bin/infra.ts`, `pnpm --filter @planpath/infra run deploy`.
- **Use the bare harness ARN, never the endpoint-qualified one.** The AgentCore console
  copies `…:harness/<name>/harness-endpoint/DEFAULT`; `InvokeHarnessCommand` rejects that
  with `ValidationException: Invalid harness ARN format`. `bareHarnessArn()` in
  `bin/infra.ts` strips the suffix and the stack throws if one slips through.
- `InvokeHarness` needs **both** `bedrock-agentcore:InvokeHarness` *and*
  `bedrock-agentcore:InvokeAgentRuntime` on the harness resource. Harnesses run on top of
  the agent-runtime API, so both authorization checks fire on one call.
- The request body is `{ question: string }`, **max 500 characters**, and nothing else.
  There is no address field, so `composeQuestion()` in `agent.ts` prefixes the address into
  the question text and the textarea is capped at 500.
- Quotas are **3 questions per Cognito identity per day** and **200 per day globally**,
  both counted in DynamoDB *before* the harness runs. Cancelling does not refund one.
- A 429 is a verdict, not a transient failure. `aws4fetch` retries 429 ten times by
  default, which turned "you are out of questions" into ~34 seconds of silent spinner —
  hence `retries: 0` on the signer and `retry: false` on the mutation.
- CORS allows `https://nswplanpath.com`, `http://localhost:5173` and `:5174`. A dev server
  on any other port is blocked. The handler echoes back whichever allowed origin the request
  came from (`ALLOWED_ORIGINS`, comma-separated); add origins in `bin/infra.ts` and redeploy.
- The frontend is hosted on AWS Amplify Hosting, built from `amplify.yml` (monorepo app root
  `apps/web`, Node 22, pnpm via corepack). `VITE_*` vars are set in the Amplify console, not
  read from `.env.local`. Needs a SPA rewrite (non-file paths → `/index.html`, 200) and the
  `nswplanpath.com` custom domain (Route 53 zone; `www` redirects to the apex). The chat API's
  CORS only allows the apex, so the `*.amplifyapp.com` preview URL can't call it unless added
  to `allowedOrigins`. `infra/lib/site-stack.ts` (S3 + CloudFront) is retired and not
  instantiated — deploying it alongside Amplify would collide on the domain's DNS and cert.
- `@types/aws-lambda` types `iam.cognitoIdentity` as `null`, which is wrong for
  Cognito-federated callers. `chat-handler.ts` narrows it back with a local `ChatEvent`
  type rather than casting at the use site.

Deliberately **not** in this stack: an AWS Budget. Budgets are account-wide, and the
separate nswtrajectory project already has a $50 monthly one on this account — a second
would double-alert on the same spend. The enforced ceiling here is the 200/day global
quota plus the kill switch:

```
aws ssm put-parameter --name /planpath/chat/enabled --value disabled \
  --type String --overwrite --region ap-southeast-2
```

Because the rules engine is not in the loop, the panel says so above the transcript and
every reply still carries the disclaimer. No verdict shown here is authoritative.

## Divergences from CLAUDE.md worth knowing

1. **Three workspace packages exist so far** — `apps/web`, `packages/shared` and `infra`.
   `services/*`, `packages/rules`, `packages/prompt`, `data/`, `scripts/` and `evals/`
   get created when their build-plan step arrives rather than as empty shells.
   `pnpm-workspace.yaml` globs `apps/*`, `packages/*`, `services/*` and `infra`.
   CLAUDE.md §Stack says Node 20 Lambdas; `nodejs20.x` was deprecated on 2026-04-30, so
   the chat handler runs `nodejs22.x`.
2. **Single `/` route.** SYSTEM_DESIGN.md §6.1 specifies `/site/$propertyId` and
   `/site/$propertyId/assess`. Those need a real `propertyId`, which needs the
   site-resolution service — so the landing page currently holds the map and chat
   together and the address is free text in `useSiteStore`. When step 1 lands, the
   address/propertyId moves into route params and out of the store.
3. **`packages/shared` is seeded, not finished.** It holds the chat contract and the
   disclaimer. `SiteContext`, `Proposal` and the assess output schema land with steps 1
   and 5.
